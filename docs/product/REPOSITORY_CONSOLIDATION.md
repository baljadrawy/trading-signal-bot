## Safe consolidation order
1. **Read-only inventory:** branches/commits/tags/PRs, current deploy SHA and image digests, workflows, scripts, documentation, worktrees, submodules, container build contexts and rollback dependencies. Save a manifest with each branch's SHA, compare status and owner decision. No host mutations during the audit.
2. **Dead-code inventory, not automatic deletion:** enumerate reachable modules and entrypoints across *all* services, Dockerfiles, cron/workflows, dynamic imports, operational scripts, recovery tools and deployed overlays. Identify unused files/dependencies with evidence, dependency graph, security and test coverage. Do not inspect or delete sealed evidence, research datasets, backups, deployment-only overlays or untracked files just because they are absent from Git imports.
3. **Preserve history:** create and verify annotated tags for production baseline and any unique branches approved for retirement; store SHA manifest and independently restorable repository backup before deletion. Never rewrite history/force-push or delete the only known good deployment ref.
4. **Decide canonical branch:** owner reviews `develop` vs current production and current `main`, then explicitly authorizes fast-forward or reviewed PR to make `main` canonical. Set GitHub default to `main`, update all CI/deployment references, branch protection and docs. Confirm the shared production host continues to run its known-good image; **changing GitHub default is not a deployment**.
5. **Merge gated work:** documentation PR #3 after review; P1 only after release gates and separate owner approval; inspect and decide on the unique refactor and diverged safety branches individually. Never bundle unreviewed code or dependency upgrades into the branch consolidation.
6. **Delete only verified obsolete branches** after default/CI/deploy/rollback dependencies are updated, preservation is verified and owner approves the deletion list. Then retire `develop` only after `main` is verified canonical and no workflows/host worktrees depend on it.
7. **One permanent branch rule:** `main` is the only long-lived branch. Feature, fix and documentation branches are temporary PR branches and deleted after approved merge. Release/rollback references use immutable tags, not permanent deployment branches. No direct unreviewed pushes to `main`.

## Explicit deletion gates
No removal of code, branch, tag, backup or history based solely on age or name. Every proposed deletion must include path/ref, reason, proof of non-use, effect on tests and production, recovery method and owner sign-off. If GitHub connector lacks branch-deletion or default-branch-setting permissions, report the limitation and supply exact owner-reviewed GitHub UI steps; do not pretend deletion occurred.
